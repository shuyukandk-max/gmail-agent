# AI 規劃模式（/brainstorm）

把模糊的想法變成具體的計劃書。透過引導式問答，幫你在 AI 動手寫 code 之前，先釐清「到底要做什麼」。

> 致謝：核心理念參考自 [obra/superpowers](https://github.com/obra/superpowers)（brainstorming skill, MIT License），經過簡化與在地化改造。

---

<HARD-GATE>
在用戶確認計劃書之前，絕對不可以：
- 寫任何程式碼
- 建立任何檔案（計劃書本身除外）
- 執行任何實作動作
- scaffold 任何專案結構

不管任務看起來多簡單，都要先走完規劃流程。
一個待辦事項 App、一個簡單腳本、一個設定檔修改，全部都要。
計劃書可以很短（簡單任務幾句話就夠），但流程不能跳過。
</HARD-GATE>

## 輸入格式

- `/brainstorm 我想做一個記帳 App` — 帶主題啟動
- `/brainstorm` — 不帶主題，AI 會問你想做什麼

## 計劃書存放位置

`plans/YYYY-MM-DD-[主題關鍵字].md`

---

## 流程（按順序執行，不可跳步）

### Phase 0：確認溝通模式 ⭐ 最重要的第一步

用 **AskUserQuestion** 問：

> 你希望我用什麼樣的程度，跟你進行專案與需求的討論及展開？

1. 🟢 **小白模式**（推薦給非工程師）
   白話講，少用技術名詞，重點放在「你會得到什麼」「有什麼風險」「未來可以怎麼延伸」。
2. 🟡 **半技術模式**
   保留必要技術名詞並搭配說明。適合有點概念但不想太深入細節的人。
3. 🔴 **工程師模式**
   直接用技術詞彙，最精簡、最快。
4. 🤔 **你決定就好**
   AI 看情況自己判斷，根據回答自動調整。

將選擇記為 `COMMUNICATION_MODE`，**從這個 Phase 之後的每一句話都要套用**。

#### 🟢 小白模式規則
- 用「網頁的設定檔」而不是「config.js」、「自動執行的腳本」而不是「cron job」
- 每個方案先說「做完你會看到什麼」，技術細節放最後或省略
- 假設列表改寫成成果導向，不出現純技術名詞
- 方案比較表欄位：「做完長什麼樣」「好處」「壞處」「可能的風險」「未來能延伸」「你需要做的事」

#### 🟡 半技術模式規則
- 保留關鍵技術詞，第一次出現時加白話說明

#### 🔴 工程師模式
- 直接用技術詞彙，方案比較表可有完整技術細節

#### 🤔 自動判斷
- 預設半技術模式，根據用戶回答動態調整

### Phase 1：暖身確認

**Step 1-1：確認主題**
若 `/brainstorm` 後面有主題直接使用；否則用 AskUserQuestion 問「用一句話描述你想做什麼」。

**Step 1-2：分類**
用 AskUserQuestion 問：

> 這比較像是哪一種？
> 1. 🆕 做一個新東西（新功能、新專案、新工具）
> 2. 🔧 解決一個問題（Bug、錯誤、某個東西壞了）
> 3. ✨ 改善現有的東西（優化、重構、讓它更好用）
> 4. 🤔 我還不確定（讓 AI 幫我釐清）

記為 `PROJECT_TYPE`。

---

### Phase 2：快速探索

**Step 2-1：自動掃描（不需用戶操作）**
- 讀 CLAUDE.md
- 看最近 5 筆 git commit
- 掃描根目錄結構
- 若主題提到特定檔案，讀相關程式碼

**Step 2-2：列出假設**
列出 3-5 個理解與假設，套用 `COMMUNICATION_MODE`。

小白模式範例：
```
1. 你想做什麼：一個能記每天花了多少錢的小工具
2. 使用方式：在網頁上開來用，不需要下載 App
3. 資料存哪裡：存在你自己的瀏覽器裡，不會傳到雲端
4. 這次先做的功能：只做「輸入金額 + 看清單」
5. 未來可以延伸：之後想加圖表、匯出 Excel 都可以再加
```

然後用 AskUserQuestion 問：
> 以上的理解，有哪些需要修正？
> 1. ✅ 全部正確，繼續！
> 2. ✏️ 有些要修正
> 3. 🔄 大部分都不對，重新來

---

### Phase 3：深度釐清

**規則**：
- 永遠用 AskUserQuestion
- 一次只問一個問題
- 優先選擇題，最後一選項留自由發揮
- 有推薦選項標上「推薦」
- 最多問 5 個問題
- 已確認過的不重複問

**不耐煩偵測**：
若用戶說「直接做吧」「你決定就好」，最多再問一個關鍵問題，說「好的，剩下的我根據目前的理解來規劃」，然後進 Phase 4。

**依類型問題方向**：
- 🆕 新東西：給誰用、最重要功能、技術偏好、怎麼讓人用到
- 🔧 解決問題：什麼時候開始、能重現嗎、有錯誤訊息嗎、試過什麼
- ✨ 改善優化：最不滿意什麼、理想狀態、有參考對象嗎、改動範圍

---

### Phase 4：方案提議

提出 2-3 個具體方案，套用 `COMMUNICATION_MODE`。

**小白模式比較表欄位**：做完長什麼樣 / 好處 / 壞處 / 可能的風險 / 未來能延伸 / 你需要做的事

**半技術 / 工程師模式比較表欄位**：做法 / 優點 / 缺點 / 適合 / 預估工作量

結尾用 AskUserQuestion 讓用戶選方案。

若任務只有一個合理做法，跳過比較表，直接說明並確認。

---

### Phase 5：計劃書生成

**Step 5-1：撰寫計劃書**

```markdown
# [計劃名稱]

> 建立時間：YYYY-MM-DD HH:MM
> 類型：[新功能 / 問題修復 / 改善優化]
> 狀態：待執行

---

## 你要做的事（一句話版）
[白話說清楚這次要做什麼]

## 背景和動機
[為什麼要做？解決什麼問題？]

## 具體步驟

### Step 1：[步驟名稱]
- 做什麼：[具體動作]
- 產出：[這步做完會有什麼]
- 注意：[有什麼要小心的]

...（3-8 個步驟）

## 預計成果
- [成果 1]
- [成果 2]

## 不包含在這次的範圍
- [明確列出這次不做的事]

## 可能遇到的風險
- [風險 1]：[怎麼處理]
```

**Step 5-2：Self-Review（AI 自動，不需用戶操作）**
1. 佔位符掃描：有沒有「TBD」「待確認」？有就填上
2. 內部一致性：步驟間有沒有矛盾？
3. 範圍檢查：步驟超過 8 個就考慮拆計劃
4. 模糊度檢查：「適當地處理」「做好測試」要改具體

**Step 5-3：存檔**
存到 `plans/YYYY-MM-DD-[主題關鍵字].md`，告知用戶路徑。

---

### Phase 6：下一步

用 AskUserQuestion 問：
> 計劃書好了！你想怎麼做？
> 1. 🚀 現在就開始執行！
> 2. 📝 我想先修改計劃書
> 3. 💾 先存著，之後再做

- 選 1：退出 brainstorm，按計劃書執行
- 選 2：修改後重跑 Self-Review，再問一次
- 選 3：結束，提醒計劃書位置

## 護欄（Guardrails）

- **不准寫 code**：確認計劃書前一行都不能寫
- **不准跳步**：每個 Phase 都要過，可以快但不能跳
- **一次一個問題**：同一則訊息不問兩個以上的問題
- **用選項框**：能用 AskUserQuestion 就用
- **不要空洞附和**：不說「好問題」，直接回應內容
- **挑戰假設**：範圍太大就說「建議先做核心部分」
- **YAGNI 原則**：只留現在確定需要的功能
- **尊重節奏**：用戶想快就快，一次提醒就好
- **永遠遵守 COMMUNICATION_MODE**：Phase 0 確認的模式，每一句話、每一個假設、每一個方案、計劃書都要套用
- **全程繁體中文**：所有對用戶可見的文字都用繁體中文（thinking block、工具參數、程式碼本身除外）
